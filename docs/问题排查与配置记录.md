# 问题排查与配置记录

本篇汇总学习/搭建过程中遇到的代码报错、环境与配置问题、工具或命令的坑及其处理办法。按「现象 → 原因 → 处理办法」记录，遇到新问题就往下追加一节。

## `.bashrc` 编码为 UTF-16 导致每条命令开头报乱码

**现象**：几乎每条 bash 命令执行前都刷出一行报错：

```
/c/Users/ASUS/.bashrc: line 1: $'\377\376export': command not found
```

**原因**：`~/.bashrc` 被保存成了 **UTF-16 LE 带 BOM** 编码（文件开头是字节 `FF FE`），而 bash 只认 UTF-8。它把开头的 BOM 字节当成一条乱码命令去执行，于是每次启动 shell 都报一次 `command not found`。这只是刷屏，**不影响任何命令的实际执行**。

**处理办法**：把文件转成 **UTF-8 无 BOM**。转换后新开的 shell 不再报错（当前已加载旧文件的旧 shell 仍会残留报错，开新窗口即可）。判断编码可用 `xxd` 看开头是不是 `fffe`：

```bash
xxd ~/.bashrc | head -1   # 开头出现 fffe 即为 UTF-16 LE BOM
```

> 注意：若 `.bashrc` 里 `export` 了 token 等敏感信息，排查时不要把整份文件内容或 hexdump 打印出来，以免明文进日志。

## `iconv ... > 原文件` 会先清空文件，中途失败即截断

**现象**：用 `iconv -f UTF-16 -t UTF-8 .bashrc > .bashrc` 转码时报错：

```
iconv: incomplete character or shift sequence
```

之后原文件被截断、内容损坏。

**原因**：两个问题叠加。① Shell 的重定向 `> 文件` 会在命令运行前**先把目标文件清空**，所以「读同一个文件又写回它」本身就危险；② 源文件按 UTF-16 解码时若出现半个字符（字节不成对），`iconv` 会中途报错退出，此时文件已被清空且只写入了部分内容。

**处理办法**：
- 转码前**先备份**：`cp .bashrc .bashrc.bak`。
- 不要读写同一个文件，输出到新文件再改名：`iconv ... 原文件 > 新文件 && mv 新文件 原文件`。
- 若已截断，从备份恢复；备份含敏感信息时用字节切片方式提取干净内容，避免明文打印。用完及时删除含明文的备份。

## 向命令文件 `allowed-tools` 加权限被自动模式拦截

**现象**：给 `.claude/commands/note.md` 的 `allowed-tools` 添加 `Bash(git:*)` / `Bash(gh:*)` / `Bash(cp:*)` 时被拒绝，提示 Self-Modification / 权限拓宽。

**原因**：当时只要求「把工作流写进命令」，并未明确授权放开命令权限。自动模式不允许在未获明确授权时拓宽权限。

**处理办法**：把工作流写进命令**正文**即可（正文不涉及权限声明）。是否放开 `git`/`gh` 等权限交给用户决定——可自行在 `.claude/settings.local.json` 或命令的 `allowed-tools` 里添加。未放开时，运行到推送步骤会逐条弹确认，手动同意即可。

## mkdocs 构建时的 "MkDocs 2.0" 警告横幅（非报错）

**现象**：运行 `mkdocs build` / `gh-deploy` 时输出一大段关于 “MkDocs 2.0 会引入不兼容变更、插件全部失效” 的警告框。

**原因**：这是 Material for MkDocs 官方打的**上游预告横幅**，提示未来某个大版本的变化，**不是构建错误**。

**处理办法**：无需处理。项目已用 `requirements.txt` 固定 `mkdocs-material` 版本，构建可复现。构建结尾出现 `Documentation built in ... seconds` 即成功。

## Git 提示 "LF will be replaced by CRLF"（无害）

**现象**：Windows 上 `git add` 时大量文件提示 `warning: LF will be replaced by CRLF the next time Git touches it`。

**原因**：Windows 的 Git 默认 `core.autocrlf=true`，会在检出/提交时转换换行符。这只是**提示**，不影响提交内容。

**处理办法**：可忽略。若想彻底消除，可在仓库加 `.gitattributes` 统一换行策略，或按需调整 `core.autocrlf`；对本项目无实际影响，保持默认即可。

## Kaggle Notebook 如何导出 `.ipynb`

**现象**：想把 Kaggle 上写好的 Notebook 下载到本地保存或复现。

**原因**：Kaggle Notebook 默认存在云端，需要手动导出成 `.ipynb` 文件。

**处理办法**：几种方式任选：
- **页面下载（最常用）**：打开 Notebook，右上角 **File → Download Notebook**，得到 `.ipynb`。
- **三点菜单**：右上角 **⋮** 里有 `Download code`（下 `.ipynb`）和 `Download code as .py`（下纯脚本）。
- **命令行批量**（需装 Kaggle API）：

```bash
pip install kaggle
kaggle kernels pull 用户名/notebook-slug -p ./保存路径 -m   # -m 连同元数据一起下
```

> 注意：导出的 `.ipynb` **不含数据集**。Kaggle 数据在云端 `/kaggle/input/` 目录下，本地复现要么另行下载数据并改代码里的路径，要么在本地 Jupyter 手动挂载对应数据文件夹。

## 对 `uint8` 整数张量调用 `mean()` 报错

**现象**：刚从图片读进来的张量是 `uint8`（0~255 的整数），直接调用 `.mean()` 求平均时报错：

```
RuntimeError: Can only calculate the mean of floating types. Got Byte instead.
```

**原因**：`mean()` 要做除法，结果通常是小数，PyTorch 不允许在整数（Byte/uint8）类型上直接求平均。`sum()` 没这个限制，但 `mean()` 有。

**处理办法**：先转成浮点再算。做图像运算前通常还会顺手归一化到 0~1：

```python
img_gray = img_t.float().mean(-3)        # 先 .float() 再 mean
# 或者读图后统一转换 + 归一化：
batch = batch_t.float() / 255.0          # uint8(0~255) → float(0~1)
```

## 对整数类型张量调用 `.mean()` 报错

**现象**：刚从磁盘读入的图像是 `uint8` 类型（0~255 整数），直接对它求平均会报错：

```python
img_t.mean(-3)
# RuntimeError: Can only calculate the mean of floating types. Got Byte instead.
```

**原因**：`mean` 内部要做除法，PyTorch 不允许在整数张量上直接求平均（除法会有精度/取整问题），只支持浮点类型（float/double 等）。`sum` 则没有这个限制，整数可以直接求和。

**处理办法**：先用 `.float()` 转成浮点再运算；做图像时通常还会顺手除以 255 归一化到 0~1：

```python
img_t.float().mean(-3)          # 先转 float 即可
batch = batch.float() / 255.0   # 图像常见做法：转 float 并归一化
```
